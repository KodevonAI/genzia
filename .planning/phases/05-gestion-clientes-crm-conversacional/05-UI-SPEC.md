# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## shadcn Gate — Decision

No `components.json` exists in this repo. Tech stack is Next.js 16 (App Router), which
would normally trigger the shadcn init prompt. **Declined without asking, by design
judgment call**: Phases 1–4 (32 plans, all merged) built a consistent, deliberate,
hand-rolled Tailwind v4 system with zero component library, zero `Dialog`/modal usage
anywhere in `app/`, and an explicit code comment in `lib/clients/list-clients.ts`
citing `STACK-WEB.md §2` as the reason the app avoids re-implementing framework
behavior in ad-hoc ways. Introducing shadcn now, mid-CRM-phase, would fork the visual
language the checker and every future phase would have to reconcile against. If this
call is wrong, override by re-running this researcher after initializing shadcn
manually — nothing below depends on shadcn being absent, it depends on matching what
phases 1–4 already shipped.

Registry safety gate: **not applicable** — no shadcn, no registries.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled Tailwind v4 utility classes (established Phases 1–4) |
| Preset | not applicable |
| Component library | none — plain HTML form elements (`input`, `select`, `textarea`, `button`), no headless-UI/Radix |
| Icon library | `lucide-react` (already a dependency; used in chat via `Paperclip`/`Send`/`X`) |
| Font | Geist Sans / Geist Mono via `next/font/google` (`--font-geist-sans` / `--font-geist-mono`, wired in `app/[locale]/layout.tsx`) |

**Known quirk, out of scope for Phase 5**: `app/globals.css` sets `body { font-family:
Arial, Helvetica, sans-serif }`, which currently overrides the loaded Geist variables
for unstyled text. Every existing component still renders in that Arial fallback, not
Geist — this phase's components should match that reality (do not silently switch to
`font-sans` on new components only, that would make Phase 5 visually inconsistent with
Phases 1–4). Use `font-mono` (`--font-geist-mono`) only where the rest of the app
already implies a fixed-width read, e.g. phone numbers in the client ficha, mirroring
no current precedent but a reasonable one-off; do not introduce it anywhere else.

## Spacing Scale

Declared values (must be multiples of 4) — these are exactly the values already in
use across Phases 1–4 (`gap-1`…`gap-8`, `px-3`/`px-4`/`px-6`, `py-2`/`py-4`/`py-8`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, badge internal padding (`py-0.5`) |
| sm | 8px | Compact stacked fields (`flex flex-col gap-1`: label→input), button vertical padding |
| md | 16px | Default gap between form fields, input/button horizontal padding, `main` horizontal padding |
| lg | 24px | Section-level `gap-6`, page header horizontal padding |
| xl | 32px | Page-level `flex flex-col gap-8`, `main` vertical padding |
| 2xl | 48px | not used yet in this app — reserved, no Phase 5 surface needs it |
| 3xl | 64px | not used yet in this app — reserved, no Phase 5 surface needs it |

Exceptions: `12px` (`gap-3`/`px-3`) is used throughout Phases 1–4 as a compact-row gap
(list-row internal gaps, inline form rows) — keep using it for the same purpose in
Phase 5 (client list rows, industry badge + assignment chip inline groups). This is an
established exception, not a new one.

## Typography

Sizes/weights are exactly what Phases 1–4 already use (confirmed by grep across
`app/`): `text-xs`/`text-sm`/`text-2xl` for size, `font-medium`/`font-semibold` for the
only two weight utilities ever applied (unweighted text renders at the browser default
regular/400).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular, no weight class) | 1.43 (Tailwind `text-sm` default) |
| Label | 12px (`text-xs`) | 500 (`font-medium`), color `text-zinc-500 dark:text-zinc-400` | 1.33 (Tailwind `text-xs` default) |
| Heading (section, e.g. "Historial de conversación") | 14px (`text-sm`) | 500 (`font-medium`) | 1.43 |
| Display (page `h1`, e.g. "Clientes" / client name) | 24px (`text-2xl`) | 600 (`font-semibold`) | 1.33 (Tailwind `text-2xl` default) |

Do not introduce `text-lg`, `text-xl`, or `text-3xl` in Phase 5 surfaces — those appear
exactly once each in the existing app (chat header logo, dashboard landing stat) and
are not part of this phase's vocabulary.

## Color

This app has no single brand-accent hue — confirmed by grep: 100% of color usage
outside zinc/white/black is semantic (green/amber/red) or a single one-off
informational blue used exactly once (`adminSeesAllNote` banner). Phase 5 must not
invent a new accent color.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` light / `#0a0a0a` dark (`var(--background)`) | Page background, `main`, ficha/list page canvas |
| Secondary (30%) | `zinc-50`/`zinc-100`/`zinc-200` light, `zinc-800`/`zinc-900` dark | Card/section borders (`border-zinc-200 dark:border-zinc-800`), row dividers (`divide-zinc-200`), muted containers (`bg-zinc-50/60 dark:bg-zinc-900/40`) |
| Accent (10%) | `zinc-900` bg + white text light / `zinc-100` bg + `zinc-900` text dark (i.e. inverse "ink", not a hue) | Reserved for exactly: the "Nuevo cliente" button on the list page, and the "Crear cliente" / "Guardar cambios" submit button on the client form. Nothing else in Phase 5 gets this treatment. |
| Destructive | `red-600` text light / `red-400` dark | Validation and save-failure error text only. **No destructive-action button exists in Phase 5** (D-14: no delete/archive UI) — this color is for error copy, never a button, this phase. |

Secondary informational note pattern (reused, not new): `bg-blue-50 text-blue-900
dark:bg-blue-950 dark:text-blue-200`, exactly as `Team.adminSeesAllNote` uses it —
reuse verbatim if the client ficha needs a one-off informational aside (e.g., "este
cliente fue creado por dictado al agente"), but do not manufacture new asides just to
use the color.

Accent reserved for: "Nuevo cliente" button (list page), "Crear cliente" / "Guardar
cambios" submit button (form). Never for badges, links, icons, or the industry
dropdown pill.

**Primary visual anchor — list page**: the "Nuevo cliente" button is the one accent-filled
element on `/dashboard/clients` — it is the page's focal point by construction, since it is
the only ink-accent surface among an otherwise all-zinc/white canvas.

## Component Inventory

No modals/dialogs anywhere in this codebase (`grep -rli dialog\|modal app/` returns
nothing) — every admin action Phases 1–4 shipped is its own route. Phase 5 continues
that: creation and edit are dedicated pages, not modals.

Proposed routes (English segment `clients`, matching the majority pattern set by
`team`/`chat`/`settings`; `bitacora` is the one existing Spanish segment, kept as a
named-artifact exception, not a rule to copy):

| Route | Purpose | New/reused components |
|---|---|---|
| `/dashboard/clients` | List + search (CLI-04/D-11) | `page.tsx` (Server Component, reads `q` search param), `client-search.tsx` ("use client", debounced input syncing the URL search param — no submit button, matches the app's light-JS bias), `client-list.tsx` (Server Component, same `<ul className="flex flex-col divide-y ...">` pattern as `AuditList`) |
| `/dashboard/clients/new` | Create form (CLI-01) | `page.tsx`, `client-form.tsx` ("use client", shared by create+edit, same field-per-`flex flex-col gap-1` pattern as `BrandForm`) |
| `/dashboard/clients/[clientId]` | Ficha (CLI-02/CLI-05/D-15/D-16) | `page.tsx` (Server Component composing the sections below), `conversation-history.tsx` (Server or hybrid Component, read-only reuse of `chat-panel.tsx`'s bubble styling), `assignment-panel.tsx` ("use client", inline disclosure reusing `assign-clients-form.tsx`'s toggle-list pattern, scoped to one client against all team members instead of one member against all clients) |
| `/dashboard/clients/[clientId]/edit` | Edit form (CLI-03) | Reuses `client-form.tsx` from `new/`, pre-filled |

Agent-side surfaces (`create_client`, `update_client`, `list_clients`, `get_client`
tools per D-08/D-10/D-12) need **no new UI** — their executions surface automatically
in the existing `/dashboard/bitacora` `AuditList`/badges (already generic by
`catalogCode`), per the established integration point. Do not build a second audit
view for client actions.

## Field Visibility Layering (CLI-05 / SEG-08 / D-06)

| Field | Layer | Ficha treatment |
|---|---|---|
| `name` | Client-visible | Plain `h1` (Display role), no marker |
| `phone` | Client-visible | Plain label/value row, no marker |
| `email` | Client-visible | Plain label/value row, no marker |
| `industry` | Client-visible | `rounded-full` pill next to the name, `bg-zinc-100 text-zinc-700 dark:bg-zinc-800 dark:text-zinc-300` (same class shape as `RISK_BADGE_CLASS.low` in `audit-list.tsx`, reused for visual consistency, not semantically risk-related) |
| `notes` | **Team-only** | The one field in this phase that gets a distinct visual treatment: enclosed in its own `rounded-lg border border-zinc-200 bg-zinc-50 p-4 dark:border-zinc-800 dark:bg-zinc-900/40` box, label preceded by a small `Lock` icon (`lucide-react`, 12px) and the caption "Solo el equipo puede ver esto." directly under the label in `text-xs text-zinc-500`. |

Per the frontend-design principle of spending boldness in one place: do not add a
"visible to client" badge to every visible field — only the exceptional case (notes)
needs to visually stand out, or the page turns into badge noise and the one boundary
that actually matters (SEG-08) gets diluted.

## Ficha Layout (CLI-02 / D-15 / D-16)

Top-to-bottom, single column, `flex flex-col gap-6` (matching `ManageMemberClientsPage`'s
section rhythm):

1. **Header row**: `name` (Display, `h1`) + industry pill inline, "Editar" link styled
   as the app's existing secondary button (`rounded-md border border-zinc-300 px-4
   py-2 text-sm font-medium dark:border-zinc-700`, same shape as the "Agregar" button
   in `assign-clients-form.tsx` — bordered, not filled, because this is a secondary
   action relative to the page's own accent-reserved primary buttons) aligned top-right.
2. **Contact info**: `phone`/`email` as two label/value pairs (Label role above,
   Body role value), `flex flex-wrap gap-6`.
3. **Assignment** (D-16): "Asignado a" label + chips of assigned member name/email
   (reuse the pill classes from the industry badge, one per member). Admins see a
   "Reasignar" text-button that expands the same checkbox-toggle list pattern as
   `assign-clients-form.tsx`, inline in the page (no navigation, no modal) — this
   satisfies D-16's "ahí mismo" (right there) requirement literally. Non-admins see
   the chips only, no control.
4. **Notes** (team-only, see Field Visibility Layering above).
5. **Placeholders — Pagos / Próximas citas** (D-15): two `rounded-lg border
   border-zinc-200 p-4 dark:border-zinc-800` boxes, same visual weight as any future
   real content so neither needs restyling when Fase 6/8 fill them in. Each shows its
   heading (Heading role) + its empty-state copy from the Copywriting Contract above.
   Do not add a call-to-action button inside either placeholder — there is nothing to
   act on yet, and a dead button reads worse than an empty box.
6. **Historial de conversación** (D-15, reused real data — no new chat UI per phase
   scope): heading "Historial de conversación" (exact string reused from
   `Bitacora.conversationHeading`), then a read-only, scrollable
   `rounded-3xl border border-zinc-200 bg-zinc-50/60 p-4 dark:border-zinc-800
   dark:bg-zinc-900/40 max-h-[28rem] overflow-y-auto` container reusing
   `chat-panel.tsx`'s exact bubble classes (`rounded-2xl px-4 py-2.5 text-sm
   shadow-sm`, contact-authored right/dark bubble, agent-authored left/light bubble).
   No input box, no attachment button, no send button — this is playback only.
