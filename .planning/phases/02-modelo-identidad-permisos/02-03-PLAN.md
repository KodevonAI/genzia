    CREATE OR REPLACE FUNCTION authorized_contacts_phone_uniqueness_guard()
    RETURNS trigger AS $$
    DECLARE
      existing_client_name text;
    BEGIN
      IF EXISTS (
        SELECT 1 FROM team_members
        WHERE team_members.agency_id = NEW.agency_id
          AND team_members.whatsapp_number = NEW.phone_number
      ) THEN
        RAISE EXCEPTION
          'phone_number % is already registered as a team member WhatsApp number in agency %',
          NEW.phone_number, NEW.agency_id;
      END IF;

      SELECT clients.name INTO existing_client_name
      FROM authorized_contacts
      JOIN clients ON clients.id = authorized_contacts.client_id
      WHERE authorized_contacts.agency_id = NEW.agency_id
        AND authorized_contacts.phone_number = NEW.phone_number
        AND authorized_contacts.client_id <> NEW.client_id
      LIMIT 1;

      IF existing_client_name IS NOT NULL THEN
        RAISE EXCEPTION
          'phone_number % is already linked to client "%" in this agency — one number belongs to exactly one client',
          NEW.phone_number, existing_client_name;
      END IF;

      RETURN NEW;
    END;
    $$ LANGUAGE plpgsql;

    CREATE TRIGGER authorized_contacts_phone_uniqueness_guard_trigger
      BEFORE INSERT OR UPDATE ON authorized_contacts
      FOR EACH ROW
      EXECUTE FUNCTION authorized_contacts_phone_uniqueness_guard();

   And the mirror direction, so the collision cannot be created from the team side:

        SELECT 1 FROM authorized_contacts
        WHERE authorized_contacts.agency_id = NEW.agency_id
          AND authorized_contacts.phone_number = NEW.whatsapp_number

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Postgres GUCs → RLS policies | The only place tenant/client scope is enforced; an unset or wrong GUC must yield zero rows, never every row and never an error |
| `client_contact` session → team-only tables | A resolved client contact is inside the agency's database but outside the team's data |
| Application write → `authorized_contacts` / `team_members` | Where a phone-number collision could be introduced |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | Cross-client leakage via missing/incorrectly-reset GUC | mitigate | `FORCE ROW LEVEL SECURITY` on both new tenant tables + `current_setting(..., true)` fail-closed NULL comparison everywhere (Tasks 1-2); proven end-to-end by plan 02-06's suite. |
| T-02-03 | Tampering | `''` vs NULL on a reused pooled connection crashing the `app.client_id` uuid cast | mitigate | `NULLIF(current_setting('app.client_id', true), '')::uuid` in 0007, mandatory from the first migration (0002's exact lesson); acceptance criteria assert zero bare casts. |
| T-02-05 | Information Disclosure | Client-contact scope reading the contact roster PII or the team roster | mitigate | `authorized_contacts_select_team_only` excludes `client_contact` (D-09, SEG-08); 0007 adds the same exclusion to team_members, client_assignments, agent_brand_config, agencies. |
| T-02-02 | Elevation of Privilege | Same phone in `team_members.whatsapp_number` and `authorized_contacts.phone_number` resolving a client contact as a team member | mitigate | Bidirectional `BEFORE INSERT OR UPDATE` triggers raising a clear exception (Task 1), same shape as `client_assignments_agency_consistency`. |
| T-02-09 | Elevation of Privilege | Client contact writing to `authorized_contacts` to authorize itself (SEG-03) | mitigate | `authorized_contacts_write_admin_only` requires `app.role = 'admin'`; no `client_contact` write branch exists, so it fails closed. |
