LD-02: the web chat is TEAM-ONLY in this phase, authenticated by the existing
Clerk session through `withTenantContext`. A client-facing web chat would need a
magic-link/OTP mechanism that exists nowhere in this codebase and belongs to the
client-portal phase (POR-01). Client contacts already reach the agent over
WhatsApp end to end, so no channel is lost by this scoping.

LD-08: non-streaming. `POST /api/chat` returns the complete reply as JSON. One
`runTurn` serves both channels; a second streaming orchestration path would
duplicate the SEG-10 interceptor's call site, which is exactly what
STACK-AGENT.md argues against.

LD-16: a web conversation is keyed by `(agency_id, channel='web',
resolved_identity_id = the team member)`. One thread per team member, no thread
management UI. `client_id` stays NULL on web rows in this phase — a team member
talking to the agent is a team-internal conversation, and per LD-03 that history
is visible to the whole team in the bitácora. Say this in the migration header
so it reads as a decision.

Create `lib/agent/web-chat.ts` (starts with `import "server-only";` — unlike the
`lib/agent/*` modules the `tsx` scripts import, this one is app-only because it
uses `withTenantContext`):

```typescript
export type WebChatInput = {
  text: string;
  attachment?: { base64: string; mimeType: string } | null;
};
export async function sendWebChatTurn(input: WebChatInput): Promise<
  { ok: true; replyText: string } | { ok: false; error: string }
>;
```
Flow:
1. `const member = await getCurrentTeamMember()`; null → `{ ok: false, error:
   "Tu cuenta todavía se está aprovisionando." }`.
2. If an attachment is present, decode it to a Buffer and call `interpretMedia`
   BEFORE opening any transaction (keep long-running work out of the tx, the
   same reason `ingest-inbound-message.ts` resolves identity before its scope).
   Enforce the same size ceilings `MEDIA_LIMITS` declares — reject oversized
   uploads with a clear error rather than buffering them.
   An audio attachment yields a transcript that is appended to `input.text`
   (LD-07 again: the model sees words, and the stored row carries them so the
   next turn has them). An image yields a content block for the current turn.
3. One `withTenantContext(async (tx) => ...)` doing, in order:
   - insert the inbound row: `channel: 'web'`, `direction: 'inbound'`,
     `clientId: null`, `fromPhoneNumber: null`, `toPhoneNumber: null`,
     `resolvedIdentityType: 'team_member'`, `resolvedIdentityId: member.id`,
     `messageType`: `'image'`/`'audio'` when an attachment was sent else
     `'text'`, `textBody`: the (possibly transcript-augmented) text,
     `metaMessageId: null`.
   - `const context = await buildAgentContextInScope(tx, agencyId, identity,
     { channel: "web", teamMemberId: member.id }, toolsFor(identity))` — the
     inbound row just written is part of that history, which is why it is
     inserted first.
   - Return `{ context, agencyId }` from the transaction. Do NOT call the LLM
     inside the transaction: an API call of unbounded latency must never hold a
     Postgres transaction open.
4. `const { replyText } = await runTurn({ actor, key, currentTurnMedia, context })`.
5. A second `withTenantContext` inserting the outbound row (`direction:
   'outbound'`, `textBody: replyText`, same identity fields, `messageType: 'text'`).
6. Return `{ ok: true, replyText }`.

The agency id comes from the Clerk `orgId` — obtain it the same way
`withTenantContext` does rather than threading it through; if that is awkward,
return it from inside the first transaction via `current_setting('app.agency_id')`
and comment the choice.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `/api/chat` | Untrusted JSON, including arbitrary base64 bytes of arbitrary size |
| Clerk session → `messages` write | A session now writes to a table previously written only by the system webhook actor |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-47 | Spoofing | A team member writing a web message attributed to another member | mitigate | `messages_web_chat_insert` pins `resolved_identity_id` to `app.team_member_id`; RLS rejects the row regardless of what the application sends. |
| T-04-48 | Elevation of Privilege | A client contact reaching the web chat | mitigate | The route is inside the Clerk-authenticated area and `withTenantContext` throws `NoTenantContextError` without a session; the insert policy additionally requires `app.role IN ('admin','member')`, which a client-contact scope never has. LD-02 means no client-facing entry point exists at all. |
| T-04-49 | Denial of Service | Huge base64 attachment | mitigate | Server-side size ceiling reused from `MEDIA_LIMITS` (5 MB image / 16 MB audio) with a 400 response before any decode-to-model path; the client-side check is explicitly documented as convenience only. |
| T-04-50 | Denial of Service | LLM latency holding a Postgres transaction | mitigate | `runTurn` is called strictly between the two `withTenantContext` blocks, never inside one — grep-asserted in the acceptance criteria. |
| T-04-51 | Information Disclosure | Provider error bodies or env values in an HTTP response | mitigate | The route logs server-side and returns a generic 500 message, matching `send-message.ts`'s established posture. |
| T-04-52 | Information Disclosure | One team member reading another's web chat in the bitácora | accept | Deliberate (LD-03/LD-16): web rows are `client_id IS NULL` team-internal history, which SEG-11 makes visible to the whole team. Documented in the migration header so it reads as a decision. |
</threat_model>
