<locked_decisions>
LD-09: no `step.waitForEvent`. The turn that proposed the action already
finished. A separate Inngest function, triggered by `agent/approval.decided`,
replays the stored tool call. Approval can take days; a suspended function
holding a turn open for days is a worse shape than a queue row plus an event.

LD-14: BOTH decisions (approve and reject) dispatch the event. The Server Action
runs under a Clerk session (`app.role` = admin/member) and therefore CANNOT
write `audit_log` — migration 0014 restricts inserts to
`app.actor = 'system_webhook'`. The background function, which runs as a system
actor, is what writes the bitácora entry for the decision. This keeps a single
audit writer (`lib/agent/audit.ts`) and a single audit-writing scope.

LD-15: who may decide — any team member whose role lets them SEE the row
(admin, or a member assigned to that client, or any member for an
agency-internal item). RLS's `approval_queue_decide_by_role` policy is the
enforcement; the Server Action adds no second role check, only the column and
status constraints RLS cannot express.
</locked_decisions>

Create `lib/agent/approvals.ts` starting with `"use server";`.

```typescript
export type DecisionResult = { ok: true } | { ok: false; error: string };
export async function approveAction(approvalId: string): Promise<DecisionResult>;
export async function rejectAction(approvalId: string): Promise<DecisionResult>;
```

Both delegate to a private `decide(approvalId, decision)`:
1. `const member = await getCurrentTeamMember()`; when null return
   `{ ok: false, error: "No estás dado de alta como miembro del equipo." }` —
   the mid-provisioning window `withTenantContext` documents, not an error state.
2. Inside `withTenantContext(async (tx) => ...)`:
   - `UPDATE approval_queue SET status = <decision>, decided_by_team_member_id =
     member.id, decided_at = now() WHERE id = approvalId AND status = 'pending'
     RETURNING id, agency_id, client_id, action_type_code, tool_name, summary`.
     The `status = 'pending'` predicate is what makes a double-click, a stale
     page or a race harmless. The column list is what makes T-04-13 (a human
     editing `tool_input` before approving) impossible through this path —
     never widen the SET clause to include `tool_input`, `tool_name`,
     `client_id` or `action_type_code`.
   - Zero rows returned means either "already decided" or "not visible to you"
     — RLS makes those indistinguishable on purpose. Return
     `{ ok: false, error: "Esa acción ya fue decidida o no está disponible para vos." }`.
   Add a comment: there is NO explicit role check here; visibility and decision
   rights are both `approval_queue_decide_by_role`'s job (LD-15), and a second
   check in code would drift from the policy.
3. After the transaction commits, `await inngest.send({ name:
   "agent/approval.decided", data: { agencyId, approvalId, decision,
   decidedByTeamMemberId: member.id } })`. Awaited, not fire-and-forget — a
   serverless invocation can be frozen before an unawaited promise resolves
   (the same reasoning `app/api/webhooks/meta/route.ts` already documents).
   Dispatch for BOTH decisions (LD-14): the background function writes the audit
   entry in either case.
4. `revalidatePath("/dashboard/bitacora")` so the list reflects the change.
5. Return `{ ok: true }`.

Header comment must state LD-09, LD-14 and LD-15, and that this module is
deliberately tiny: the only thing a human's session is allowed to do to the
queue is flip a status.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Clerk session → approval decision | A browser request flips a status that authorizes a real side effect |
| Stored proposal → delayed execution | The tool input was produced by a model at some earlier time and is replayed later |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-42 | Elevation of Privilege | A member deciding on an unassigned client's action | mitigate | `approval_queue_decide_by_role` gates both visibility and the UPDATE with the same predicate; the Server Action adds no bypass and has no service-role path. Asserted in 04-08 (assertions 20/23) and 04-12. |
| T-04-43 | Tampering | Escalating a proposal by editing `tool_input` before approving | mitigate | The Server Action's SET clause is limited to `status`/`decided_by_team_member_id`/`decided_at` — grep-asserted — and the replay function re-runs the interceptor's scope cross-check on the stored input rather than trusting it. |
| T-04-44 | Tampering | Double execution from a double-click or an Inngest retry | mitigate | `WHERE status = 'pending'` on the UPDATE makes only the first decision effective; the replay function returns early unless the row is still `approved`/`rejected`, and `step.run` memoises the completed execution. |
| T-04-45 | Repudiation | A decision with no record of who made it | mitigate | `decided_by_team_member_id` + `decided_at` are set in the same statement as the status; the background function writes an `audit_log` row with `approval_id` linking back. |
| T-04-46 | Denial of Service | An approved action silently lost on failure | mitigate | Step 3 does not swallow errors; step 4 records `failed` with the real message on the queue row and in the bitácora, so a failure is visible in the UI instead of looking like "still pending". |
</threat_model>
