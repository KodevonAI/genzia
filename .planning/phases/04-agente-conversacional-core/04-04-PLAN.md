<objective>
Build `buildAgentContext` — the single, security-critical function that turns
"an agency, an identity and a conversation" into `{system, tools, messages}`
for one LLM turn. Nothing else in the codebase is allowed to read `messages`
or `agent_brand_config` for agent purposes.

Purpose: SEG-05 says the conversation's scope determines the data the agent can
use "nunca por instrucción/filtro, sino porque el sistema no carga datos fuera
de ese alcance". This function is where that becomes structural: it opens the
correct RLS scope and then reads without adding a single application-level
client filter, so the boundary is enforced by Postgres, not by remembering to
write a WHERE clause.
Output: three modules, no I/O beyond the database.
</objective>

<locked_decisions>
LD-05: history is capped at the most recent `HISTORY_MESSAGE_LIMIT = 40`
messages of the conversation, ordered by `created_at`. No token counting, no
summarisation in this phase — a hard row cap is the cheapest defence against
the unbounded-cost failure mode and it is trivially verifiable. The cap lives
as an exported constant so a later phase can replace the policy in one place.

LD-07: only the CURRENT turn carries raw media bytes into the model. Historical
rows are rendered as text: an audio row shows its transcript (plan 04-05 writes
the transcript back into `messages.text_body` after transcribing), an image row
shows the literal placeholder `[imagen enviada por el usuario]`. Re-downloading
every historical image from Meta on every turn is an unbounded cost with no
requirement behind it.

LD-02: web chat is TEAM-ONLY in this phase, authenticated by the existing Clerk
session via `withTenantContext`. Client contacts reach the agent through
WhatsApp, which is already end-to-end. A client-facing web chat needs a
magic-link/OTP mechanism that exists nowhere in this codebase and belongs to
the client-portal phase (POR-01). This is why `buildAgentContextInScope` takes
a transaction rather than opening one: the web path's scope is opened by a
`server-only` Clerk module that a `tsx` verification script cannot import.
</locked_decisions>

Create `lib/agent/build-context.ts` exporting:

```typescript
export const HISTORY_MESSAGE_LIMIT = 40;

/** Core reader. Takes an ALREADY-SCOPED transaction — never opens one. */
export async function buildAgentContextInScope(
  tx: IdentityTx,
  agencyId: string,
  identity: ResolvedIdentity,
  key: ConversationKey,
  tools: Anthropic.Messages.Tool[],
): Promise<AgentContext>;

/** WhatsApp/phone-resolved entry point: opens withResolvedIdentityContext. */
export async function buildAgentContext(
  agencyId: string,
  identity: ResolvedIdentity,
  key: ConversationKey,
  tools: Anthropic.Messages.Tool[],
): Promise<AgentContext>;
```

`buildAgentContextInScope` does exactly four things, in order:
1. Read `agent_brand_config` for `agencyId` (`agentName`, `tone`). A missing row
   is normal — pass `{ agentName: null, tone: null }`.
2. Read history from `messages` with, and ONLY with, these predicates:
   - `agency_id = agencyId`
   - for `key.channel === "whatsapp"`:
     `channel = 'whatsapp' AND (from_phone_number = key.counterpartPhoneNumber
      OR to_phone_number = key.counterpartPhoneNumber)`
   - for `key.channel === "web"`:
     `channel = 'web' AND resolved_identity_id = key.teamMemberId`
   - `ORDER BY created_at DESC LIMIT HISTORY_MESSAGE_LIMIT`, then reverse in
     memory to chronological order.
   There is NO `client_id` predicate and NO role branch in this query. Add a
   comment saying so explicitly and why: adding one would be exactly the
   app-level filter SEG-05 rejects, and it would mask a broken RLS policy
   instead of failing loudly. The policy from migration 0015 is the boundary.
3. `system = buildSystemPrompt(identity, brand)`.
4. `clientId = identity.type === "client_contact" ? identity.clientId : null`.
   (For a team member the turn is not scoped to one client; a tool call names
   the client explicitly and the interceptor re-checks it.)

`buildAgentContext` is a thin wrapper:
`return withResolvedIdentityContext(agencyId, identity, (tx) =>
buildAgentContextInScope(tx, agencyId, identity, key, tools))`.

Header comment must state, prominently: this is the only function in the
codebase permitted to read `messages` for agent context; it is called fresh on
every turn and its result is never cached across turns; and the web-chat path
(plan 04-10) calls `buildAgentContextInScope` with a `withTenantContext`
transaction because that helper is `server-only` and cannot be imported here.

Do NOT add `import "server-only"` to this file.
