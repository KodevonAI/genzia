<objective>
Build the SEG-10 engine: every tool call Claude proposes is intercepted,
classified against the static `agent_action_catalog`, and either executed
immediately (low) or queued for human approval and NOT executed (high). Both
branches write the bitácora entry SEG-11 requires.

Purpose: this is the requirement that makes the agent safe to point at real
clients. It is also, per OWASP's own current guidance, the main structural
mitigation against prompt injection — model output is treated as a proposal
subject to deterministic policy checks, never as a command.
Output: a tool registry with two real tools, one audit writer, one interceptor.
</objective>

LD-12: tool availability is decided by identity, not by prompt. `toolsFor()`

not act on their behalf. This means a client contact literally cannot emit a
tool_use block, because no tool is offered.

```typescript
export const TOOL_TO_CATALOG_CODE: Record<string, string> = {
  send_payment_reminder: "payment_reminder",
  draft_client_content: "new_client_content",
};

export async function classifyAndExecute(
  toolUse: { id: string; name: string; input: unknown },
  actor: TurnActor,
): Promise<Anthropic.Messages.ToolResultBlockParam>;
```

Steps, in this exact order — each one needs a comment explaining what it
prevents:

1. **Map, don't trust.** `const code = TOOL_TO_CATALOG_CODE[toolUse.name]`. If
   undefined → return an `is_error: true` tool_result
   (`` `Herramienta no reconocida: ${toolUse.name}` ``) with NO catalog read and
   NO execution. The catalog code comes from a code-level map, never from
   anything in `toolUse.input` — SEG-10 and STACK-AGENT.md §6 both forbid the
   model influencing its own risk classification.

2. **Scope cross-check (RESEARCH.md Pitfall 4).** Extract
   `input.clientId` when the tool declares one. Reject, with an
   `is_error: true` result and no execution, when:
   - it is not a string matching
     `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`, or
   - `actor.identity.type === "client_contact"` and it differs from
     `actor.identity.clientId`, or
   - `actor.identity.type === "unknown"` (an unknown sender can never target a
     client).
   For a `team_member`, do NOT re-implement the assignment check here: the
   tool's own reads run inside the member's RLS scope, so an unassigned client
   yields no contact and `deliverToClient` fails closed. Say that in a comment
   so nobody adds a duplicate, driftable check later.

3. **Classify.** Read the catalog row: `db.select().from(agentActionCatalog)
   .where(eq(agentActionCatalog.code, code))` via the plain unscoped `db` —
   allowed here because `agent_action_catalog` is platform-global with no RLS
   and a SELECT-only grant (migration 0006). A missing row is a programming
   error: return an `is_error: true` result and write an audit entry with
   status `failed`.

4. **Low branch.** `const output = await executeTool(toolUse.name, toolUse.input, actor)`,
   then `writeAuditLog({..., riskLevel: "low", status: "executed", summary:
   describeToolCall(toolUse) })`. Return `{ type: "tool_result", tool_use_id:
   toolUse.id, content: output }`. If `executeTool` throws, catch it, write an
   audit entry with status `failed` and the error message, and return an
   `is_error: true` result — a tool failure must not abort the turn.

5. **High branch — execution is NOT attempted.** Insert into `approval_queue`
   via `withSystemWebhookContext` with `status: 'pending'`, the full
   `toolInput`, `toolUseId`, `channel`, `conversationPhoneNumber`,
   `requestedByIdentityType`/`Id` from `actor.identity`, and
   `onConflictDoNothing` on the `(agencyId, toolUseId)` unique index; re-select
   the row id when the insert was a no-op so a retried step reuses the same
   approval. Then `writeAuditLog({ riskLevel: "high", status:
   "pending_approval", approvalId })`. Return a tool_result whose content is
   exactly:
   `"Esta acción requiere aprobación del equipo antes de ejecutarse. Quedó en la cola de aprobación y el equipo la va a revisar."`
   (Spanish, addressed to the model so it can relay it honestly — SEG-09's
   spirit: never claim an action happened when it did not.)

Also export a small `describeToolCall(toolUse): string` producing the human
one-liner stored in `summary` — e.g.
`` `send_payment_reminder → cliente ${clientId}` ``. Never put the full
`tool_input` in `summary`; it is already stored as jsonb on the queue row.
