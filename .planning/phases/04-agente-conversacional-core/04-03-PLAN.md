<locked_decisions>
LD-04 (from 04-01): team-only visibility. `approval_queue` follows
`audit_log`'s new shape exactly — admin sees all, member sees
`client_id IS NULL` plus assigned clients, and there is NO `client_contact`
branch. A client contact must never learn that an action about them is awaiting
internal approval.

LD-09: high-risk actions are NOT executed by a suspended Inngest function
waiting on an event. The turn that proposes them finishes immediately, and a
separate function (plan 04-09) executes the action when a human decides. That
is why this table carries everything needed to replay the tool call later
(`tool_name`, `tool_input`, `client_id`, `conversation_phone_number`,
`channel`), not just a reference to a live run.
</locked_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Agent turn → approval_queue | The agent writes proposals under a system actor; the subject of a proposal must never see or alter it |
| Human decision → approval_queue | A team member may flip status, but only for rows their role lets them see |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-11 | Information Disclosure | `approval_queue` visibility | mitigate | No `client_contact` branch in any of the three policies; a client-contact scope matches none and reads zero rows. Asserted in plan 04-08's suite. |
| T-04-12 | Information Disclosure (SEG-06) | Member seeing other clients' pending actions | mitigate | Member branch joins `client_assignments` with the `NULLIF(...)::uuid` cast; identical predicate reused for the UPDATE policy so visibility and decision rights cannot drift apart. |

Documented in the migration header. |
| T-04-14 | Repudiation | Losing who approved what | mitigate | `decided_by_team_member_id` + `decided_at` are written in the same statement as the status flip; `audit_log.approval_id` links the bitácora line back. |
