<locked_decisions>
LD-08: turns are non-streaming. `runTurn` returns the complete reply text. A
tool-calling loop is not linearly streamable without a second orchestration
path, and neither the phase goal nor WA-05 asks for token-by-token output. The
same `runTurn` therefore serves WhatsApp (this plan) and web chat (plan 04-10).

LD-13: `MAX_TOOL_ITERATIONS = 5`. When the model still wants a tool after the
fifth round, the loop stops and the agent replies with a plain message saying it
could not complete the request — never an infinite loop, never a silent
truncation with no reply.

LD-05 / LD-07 (from 04-04 / 04-05) apply here: history is capped at 40 rows, and
the current turn's audio transcript is written back into the inbound row's
`text_body` so later turns read it as plain text.
</locked_decisions>

```typescript
export const MAX_TOOL_ITERATIONS = 5;
export const MAX_OUTPUT_TOKENS = 1024;

export type TurnMediaInput =
  | { kind: "text"; text: string }
  | { kind: "image"; block: Anthropic.Messages.ImageBlockParam };

export async function runTurn(params: {
  actor: TurnActor;
  key: ConversationKey;
  /** Extra content for THIS turn only — the current image block, if any. */
  currentTurnMedia?: TurnMediaInput | null;
  /** Pre-built context, for the web path which owns its own transaction. */
  context?: AgentContext;
}): Promise<{ replyText: string; iterations: number; provider: string }>;
```

Implementation:
1. `const context = params.context ?? await buildAgentContext(actor.agencyId,
   actor.identity, key, toolsFor(actor.identity))`.
2. `const messages = [...context.messages]`. If
   `currentTurnMedia?.kind === "image"`, append its block to the content of the
   LAST user message (or push a new user message containing it when the last
   message is not a user turn). Comment: the inbound row is already persisted
   and therefore already present in `context.messages`; only the raw image bytes
   are not, which is why they are merged rather than pushed as a duplicate turn.
3. Loop `for (let i = 0; i <= MAX_TOOL_ITERATIONS; i++)`:
   - `const { client, provider } = getAnthropicClient()`
   - `const res = await client.messages.create({ model: MODEL_FOR_TASK.main,
     max_tokens: MAX_OUTPUT_TOKENS, system: context.system, tools:
     context.tools, messages })` inside try/catch: on error `reportLlmFailure()`
     then rethrow; on success `reportLlmSuccess()`.
     The system prompt is the TOP-LEVEL `system` field. A `{role:"system"}`
     entry inside `messages` is prohibited — it defeats prompt caching and is
     the exact symptom RESEARCH.md Pitfall 3 warns about. Say so in a comment.
   - If `res.stop_reason !== "tool_use"`: join the `text` blocks and return
     `{ replyText, iterations: i, provider }`.
   - Else: push `{ role: "assistant", content: res.content }`, run every
     `tool_use` block through `classifyAndExecute(block, actor)` **sequentially**
     (never `Promise.all` — two tool calls that each send a WhatsApp message
     must not interleave), and push `{ role: "user", content: toolResults }`.
4. After the loop: return
   `{ replyText: "No pude completar esa solicitud en este momento. Ya quedó registrada y el equipo puede revisarla.", iterations: MAX_TOOL_ITERATIONS, provider }`.
   Never return an empty `replyText` — an empty WhatsApp send is a Graph API
   error, and silence is indistinguishable from a crash for the person waiting.
   Same guard for a normal completion whose joined text is empty (the model
   returned only non-text blocks): substitute `"Listo."`.

No `import "server-only"` — the verification suite imports this under `tsx`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Inngest event payload → RLS scope selection | The event carries the identity that decides which scope opens; a wrong or forged value would widen every read in the turn |
| Agent reply → a real person's phone | Anything `runTurn` returns is delivered to a human over WhatsApp |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-33 | Spoofing | Forged `whatsapp/message.received` event | mitigate | The only producer is the webhook route, which runs after `verify-meta-signature.ts`'s HMAC check and only on `outcome === "ingested"`. The Inngest serve endpoint validates its own signing key. No new producer is added. |
| T-04-34 | Information Disclosure (SEG-05) | Turn reading outside the sender's scope | mitigate | `runTurn` never queries anything itself; all reads go through `buildAgentContext`, which opens `withResolvedIdentityContext` for the event's identity. Asserted live in plan 04-08. |
| T-04-35 | Denial of Service (cost) | Unbounded tool-call loop | mitigate | `MAX_TOOL_ITERATIONS = 5` plus `HISTORY_MESSAGE_LIMIT = 40` and `max_tokens: 1024`; the loop exit path still produces a reply. |
| T-04-36 | Tampering | Duplicate reply to a real phone after a retry | mitigate | Five separate named `step.run` blocks so Inngest memoises the completed send; plus `onConflictDoNothing` on `(agency_id, meta_message_id)` with the partial-index predicate repeated (the exact bug fixed in 03-08). |
| T-04-37 | Repudiation | A reply with no history row | mitigate | `persist-outbound-row` runs as its own step after the send; a failure there retries without re-sending, so the row eventually exists for every delivered reply. |
| T-04-38 | Denial of Service | Media failure killing the turn | mitigate | `interpret-media` catches and degrades to a placeholder; the person still gets an answer that honestly says the file could not be processed. |
